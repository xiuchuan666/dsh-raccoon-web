### 为什么少了这么多

不是"效率高"，是**估时错在三处**：

1. **T-08 的 4–8h 是给"自己复刻 SSE 状态机"的**。发现 pi-ai 已支持 `reasoning_content` + 有 `onPayload` 钩子之后，这件事从"重写 1344 行协议"变成"68 行包装"。**这是估时当时不掌握的信息，不是执行得好。**
2. **T-04 的 12.2h 里有一半是"调试到手机能扫"**。用 `verify-qr.mjs` 接 OpenCV 真解码，把"手机试"变成"脚本跑"，反馈周期从分钟级降到秒级。**估时时没算这个杠杆。**
3. **T-01/T-03/T-09/T-10 的高估来自"从零设计"的假设**，实际上参考实现已经把形状定死了（`isLoopback` / `readRequestBody` / client.js 的 slot 注册 / `assemblePiAiAdapter` 的装配）。

### 下次估时该怎么改

| 类别 | 修正 |
| --- | --- |
| 有现成参考实现的骨架类 | 按估时的 1/3 算 |
| 需要跟真实外部系统对齐的（协议、认证） | 保持估时 —— 这部分省不了，只是这次前人已经逆向好了 |
| 需要"自己造轮子"的（QR 编码器） | **先花 30 分钟确认能不能用现成库/现成钩子，再估**。T-04 与 T-08 都是这一条 |
| 客户端 UI | 按估时的 1/3 算（组件独立、无状态交互） |

**更重要的是**：这份 WBS 剩下的价值不是"天数"，是**任务分解的粒度**。粒度和依赖关系是对的（T-04 与 T-05 可以并行、T-08.6 是 M3 的硬阻塞），只是绝对时长不可信。

### 可以砍的

如果要压缩到 6 天：

| 砍掉 | 省 | 代价 |
| --- | --- | --- |
| T-04 自实现 QR → 引 `qrcode-generator` | 11h | 多一个依赖（40 KB，无传递依赖） |
| T-08.6/08.7 自定义 Api → 用 `openAICompletionsApi` | 6–10h | 失去思考通道 |
| T-10.9 识图标记 + T-09.11/09.12 探测 | 4h | 用户可能被丢图的模型坑 |
| T-10.10 诊断块 | 1h | 报障时信息少 |
| T-11.2/11.3 宿主层单测 | 2.5h | 存储层的 bug 只能靠手工发现 |

**建议的砍法**：先砍 T-04（引库），再砍 T-11.2/11.3。**不要砍 T-08.6** —— 思考通道是这个项目相对 sensenova 版本的核心差异。

1. **否定结论也要写清证据路径。** E-006 当初只写"`~/.box-agent/config/auth.json` 不存在"，没写"我查了哪几个路径、没查哪个"。结果一个漏掉的路径让整条登录路线白做一轮。**以后"没找到 X"必须附"查过的路径列表 + 排除理由"。**
2. **破坏性动作不能放在只读观察路径上。** 4 张码全废不是协议问题，是"看一眼状态"的脚本顺手触发了 `login-start`（而它第一件事是 `cancel()`）。**取码脚本与盯码脚本必须是两个互不调用的入口。**
3. **没有 `.d.ts` 的依赖，先读 `.js` 再落笔。** 内核三处纠正（`replace()` 返回 void 且参数是 `string[]`、`auth.apiKey.resolve()` 必须真返回 `{auth:{apiKey}}`、`profiles()` 用引用相等做 memo）全是"照抄形状但没读实现"。第一轮 WBS 的 T-08 估时之所以虚高又虚低，根子都在这。
4. **路线一变，立刻标过期，别攒到收尾。** R-11 之所以占掉后半程，是因为 ADR-0001 被推翻时只改了代码、没同步把 7 篇设计文档标成旧口径，最后得逐篇重写。**`AGENTS.md` 第 2 条不是形式主义。**
