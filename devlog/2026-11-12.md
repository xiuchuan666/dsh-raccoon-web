## 今天做了什么

### 1. 用户报的三个 bug：先取证，再改代码

用户原话（m07683）三件事：账号池扫码加号「微信扫完点确认，显示二维码已过期或已被使用，插件接收不到登录信息」；
在客户端换第二个号并导入后「第一个账号又消失了」；换号期间发消息「显示 API 密钥无效」。

三条**分别**是三个不同的根因，不是同一个：

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 扫码加号收不到登录 | **上游把 `/login/mp` 页面下线了**（E-040） | 加号主路线改浏览器 loopback（ADR-0012） |
| 换号后旧号消失 | `writePool()` 是整表原子写，`this.accounts` 只是内存快照 | `mergePools()` + `Host.savePool()` |
| 换号后报 API 密钥无效 | 401 时直接 `markDead()`，没重读 `auth.json` | `rereadDesktopAuth()` 先重读再判死 |

第一条花的时间最多，也最值得记：**我先猜错了三次**。

- 猜 `web-auth.ts` 的 `CODE_RE` 是双反斜杠 → 逐字符码点验证，`codes` 里就是 `92,100`（`\` + `d`），
  只有一个反斜杠。**这条假线索冤枉了两次**（11-11 一次、11-12 又一次），已经写进 troubleshooting 让人别再动。
- 猜缺 UA / 缺 `registration_attribution` → 补上之后行为**完全没变**，仍然是 `pending`。
- 猜微信端扫的是旧码 → 加了 `lastPoll` 诊断字段，实测 `lastPoll` 恒 `pending`，说明服务端根本没认领。

真正的判据是**拿 11 组 UA / header 组合去打 `/login/mp`**：微信 iPhone、微信 Windows、Chrome 131、
`curl/8.0`、无 UA、`x-requested-with: com.tencent.mm`、`referer: servicewechat.com`、完整 `sec-fetch-*`
—— **全部 404**。再用 `_rsc=1` + `accept: text/x-component` 拿到 200 的 RSC 流，里面明确写着
`404: This page could not be found.`（`notFound`）。**这才叫"路由不存在"，不是鉴权失败。**

### 2. 换到官方换账号真正走的那条路

用户 m07715 给了一条关键提示：「客户端会打开浏览器，让我先在浏览器里面登录，然后浏览器再把客户端重新拉起来」。
顺着这句去读 asar，`webLogin.js` / `webLoginLoopback.js` / `desktopLogin.js` 三个文件把整条链路讲清了：

```
用户点「登录」 → 打开 /authorize?login_source=desktop&appname=商汤小浣熊客户端
                 &desktop_callback=loopback&redirect=http://127.0.0.1:<port>/auth/callback&state=<64hex>
浏览器里登录完 → 302 到 127.0.0.1:<port>/auth/callback?code=<一次性授权码>&state=<同一个>
本机服务收下 → POST /api/web/auth/v1/login_with_authorization_code {authorization_code}
             → { code: 0, data: { access_token, ... } }
```

真网关两条都验过：`/authorize` 对裸请求 **200 / 32175 字节**（标题「客户端授权 | 商汤小浣熊」）；
换码端点对假 code **400 `200035 authorization_code_not_found_error`** —— 它真的在校验，不是摆设。

### 3. 写 `src/protocol/loopback.ts`（405 行）并接进宿主

护栏是照官方 `webLoginLoopback.js` 逐条抄的，不是自己想的：

- `state` 用 `randomBytes(32)`（64 hex），比对用 `timingSafeEqual`；
- 只接受 `GET` + 精确路径 `/auth/callback`；参数只许 `code` / `state`，各出现且只出现一次；
- `code` 非空、≤4096、不含控制字符；`url.length ≤ 8192`、不许有 hash；
- 只监听 `127.0.0.1` 随机端口，`maxConnections = 8`、`headersTimeout = 5000`、`requestTimeout = 10000`；
- 一次性（`settled` 保证），收尾 `server.close()` + `closeAllConnections()`，`timer.unref()`；
- 结果页带 `Cache-Control: no-store` / `Referrer-Policy: no-referrer` / CSP `default-src 'none'`。

宿主侧新增 `pool-add-browser` / `pool-add-browser-cancel` 两个 action、`status.browser` 块
（**不含 code、不含 token**）、`dispose()` 里必须 `closeBrowserLogin()`（它在真的监听一个端口）。

### 4. 顺手修掉的两处「上游语义抄错」

- **`canceled` 不是结束，是换码。** 官方网页端是 `if("canceled"===r) return void c();` —— 立刻重开一张。
  我们原来把 `phase` 打成 `none`，用户手机上点一下「取消本次登录」，界面就留一张作废的码。
  现在 `reissue()` 自动换码，上限 `MAX_REISSUES = 3`（服务端若对坏 code 一直回 canceled，
  无限换码就是 2 秒一次的请求风暴，而且用户毫不知情）。**`start()` 必须拆成 `start()` + `beginRound()`**，
  否则 `reissue()` 走 `start()` 会把计数清零，上限永远触发不了 —— 这个坑第一次写的时候就踩了。
- **`expired_at` 要采纳。** 服务端在 `logging` 时第一次给出它，官方就在那一刻记下来；我们原来只用自己的 5 分钟。

# 第二条日志（01:35–02:10）：把「一键签到」真的接上界面，并让签到失败影响选号

没有新用户输入。上一轮把 0.2.1 的代码和文档收口之后，回头逐条读 `actionPoolCheckin()`
与 `PoolSection`，发现两个**功能已经实现、但用户永远看不到效果**的缺口。两个都修了。

## 今天做了什么

### 1. `pool-checkin` 的逐号结果从来没显示过

宿主一直在返回 `results: [{ id, result: "already"|"granted"|"error", message? }]`，
`PoolSection.run()` 拿到结果后只看了 `result.ok` 和 `login`，`results` 直接丢掉了。
用户点「一键签到」看到的是：按钮转两秒 → 什么都没有变。这是最糟的一种失败 ——
不是报错，是**静默**，用户会以为按钮没绑事件。

改法：`PoolSection` 加一个 `checkins` state（`{ [id]: row }`），`run()` 里对
`action === 'pool-checkin'` 收集成 map，账号卡片上多渲染一行：

- `granted` → 绿色「已签到」
- `already` → 绿色「今日已签」
- `error` → 红色「签到失败 · 上游原文第一行」（`.split('\n')[0]` 截断，上游文案是多行）

新一轮签到开始前清空，否则失败的号会一直挂着红字。加了 `data-raccoon-checkin` 属性方便排查。

### 2. 签到失败不影响选号 —— 坏号会被一直选中

`actionPoolCheckin()` 的 catch 只 `results.push({result:"error"})`，**不动 `measure`**。
后果很具体：一个凭据已经废掉的号，卡片上仍然显示「可用」，`sortForUse()` 仍然会选它，
下一轮对话继续 401，`recordMeasure()` 才把它标成 `dead` —— 白让用户看一次「API 密钥无效」。

为什么签到这个信号应该更可信：它是**用户主动发起的、每天一次**的动作，不存在"对话中途
上游抖动"那种噪声；而 `onResponse` 那条通路是每个响应都跑一次，只能保守。

改法：catch 里走 `classifyMeasure()` + `shouldPersistMeasure()`：

- `AUTH` → `dead`（`until = MAX_SAFE_INTEGER`，要靠手动「测试」或重新登录回池）
- `RATE_LIMIT` → `limited`（30 分钟）
- `TIMEOUT` / `TRANSPORT` → `flaky`（30 分钟，自动回池）
- `EMPTY`（`402` 或余额不足文案）→ `empty`（到北京零点）
- 其它（含 HTTP 400）→ `undefined`，**不记**（与 `recordMeasure()` 同一条铁律：与账号无关的失败不该让好号白躺）

写盘走 `savePool()`（先 `mergePools()` 再整表写），与 `actionPoolTest()` 同一理由：
签到是低频动作，多读一次盘换"不抹掉别的号"是划算的。

**类型上踩了一下**：`MeasureInput.kind` 只收
`"TIMEOUT" | "TRANSPORT" | "AUTH" | "RATE_LIMIT" | "SERVER" | "EMPTY_RESPONSE"`，
而 `RaccoonErrorKind` 多了 `INVALID_REQUEST` / `ABORTED`。直接传会报
`TS2322: Type '"INVALID_REQUEST"' is not assignable to ...`；先写成
`kind === "AUTH" || ... || kind === "EMPTY_RESPONSE" ? { kind } : {}` 又报
`TS2367: types '"INVALID_REQUEST" | "ABORTED" | undefined' and '"EMPTY_RESPONSE"' have no overlap`
（TS 已经把前几个 `||` 收窄掉了）。最后落成一个显式映射表 `ACCOUNT_KINDS`
（`Partial<Record<RaccoonErrorKind, …>>`），既过类型又自带文档：**两套词表刻意不同**，
错误分类面向"这次请求发生了什么"，测量分类面向"这个账号现在能不能用"。

### 3. `dead` 的说明文案写死了「需要重新扫码」

号池成员的来源有三种（`qr` / `desktop` / `browser`），只有 `qr` 能靠扫码恢复。
桌面端凭据过期的人看到「需要重新扫码」会被引导到一条他从来没走过的路上。
`classifyMeasure()` 两处（`kind === "AUTH"` 与 `status 401/403`）都改成来源中性的
「登录已失效，需要重新登录这个账号」。

### 4. 真宿主上跑了一次真签到

`POST ?action=pool-checkin`（端口 52091，`build 2026-11-12T02:05`）：
池里两个号，`7b86c892…`（旧号，凭据已废）→ `error`，上游原文
`{"code":200003,"message":"authorization_verify_error"}`；`f575c172…`（当前桌面端账号）→ `already`。
修完之后 `status.pool.accounts[0].measure` 立刻变成
`{"state":"dead","note":"登录已失效，需要重新登录这个账号"}` —— 这就是第 2 条要的行为。
