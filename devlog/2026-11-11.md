## 今天做了什么

### 1. 修「输入框看不到积分」+「设置里插件页面空白」（用户 m05082 的前两条）

用户报的是两个现象，以为是两个 bug，还怀疑「之前清理宿主时删掉了一个重复注入，是不是那时搞坏的」。

**实际是同一个根因，而且与删注入无关。**

DSH 从 `0.2.1-rc.5` 升到了 `0.2.2-rc.1`。新版 `locale.register()` 在同一个 namespace 的同一个 locale 已存在时**抛错**：

```
locale namespace "dsh-raccoon-web" already has locale "zh"
```

而 `client.js` 的 `apply(ctx)` 第一句就是 `ctx.effect(() => ctx.locale.register(...))`。这一句抛错后，**后面三个 `slots.inject` 全部没执行** → 三个 slot 一个都没注册 → 积分药丸消失 + 设置卡空白。

触发条件是 profile 里同一个包被加载两次（用户手工清理插件时很容易留下）。

修法（`packages/dsh-raccoon-web/client.js`）：

- `bindTranslator(ctx)`：`locale.bind()` 拿不到时回落 `key => key`，并 `console.warn`。
- `guard(label, step)`：每个 slot 注册各包一层 try/catch + `console.error`。
- `apply` 重写成「locale 单独兜 + 三个 slot 各自兜」，**任何一步失败都不能连累其它两步**。

同时发现第二个症状有**独立原因**：用户默认模型是 `workbuddy-global`，而旧 `CreditPillGate` 只在 `selected.provider === PROVIDER_ID` 时渲染 → 药丸永不出现。改成总是显示，选中的不是小浣熊时按钮降透明度 + 详情面板加一行 `pillOtherModel` 解释。

**关键工具**：新增 `scripts/smoke-client-apply.mjs`。用 `node:vm` 在 Node 里加载 `client.js`，注入照抄 0.2.2 语义的替身 ctx（`locale.register` 重复抛错、`slots.register` 校验 `options.name`），离线跑 `apply`。`--twice` 复现重复加载。

验证它能抓 bug：拿 `git show :packages/dsh-raccoon-web/client.js`（旧版 51951 字节）跑 `--twice`，直接报
`- 第二次 apply 抛错且没被兜住：locale namespace "dsh-raccoon-web" already has locale "zh"`
`- 第二次 apply 应仍注册 3 个 slot（locale 重复不算致命），实际 0`
→ **根因确证**。

### 2. 从零做账号池（用户 m05082 的第三条）

需求原文：「我想建立一个号池，插件的设置页面应该能统一管理这些账号，可以参考当前已经安装的 workbuddy 插件。其中一个账号用完了额度，可以自动切换下一个账号。然后带有一键签到功能，把所有的账号都一键签到了。每个账号尽量像 workbuddy 插件一样，给他一个独立的环境，防止封号。」

#### 先做调研，不照抄形状

- 读 `~/.dsh/profiles/desktop/node_modules/dsh-connect-workbuddy/README.md`（141443 字节）的账号池章节，把它踩过的坑全抄进 ADR：空池绝不退化成"全部账号"、HTTP 400 不换号、流中途断开不换号、排序里"快过期先花"必须排在"余额高"**之前**（issue #70 的真实病例：196.4 分当天作废）、签到按钮不能挂在开关上、草稿与观测必须分离。
- 逆向官方 asar（336MB）枚举出 **57 个 `/api/web/...` 端点**，找到三个号池地基：
  - `POST /api/web/desktop/v1/login/points/grant` —— 签到写接口（**无 body**）
  - `POST /api/web/auth/v1/refresh` —— token 刷新（之前判"没有 refresh grant"是错的）
  - `X-Client-Device-ID` —— 唯一的设备身份头

#### 实机验证三个端点

- 签到：连续两次 200 `{"code":0,"message":"success","data":{"granted":false,"popup":null}}`（262ms / 158ms）→ **幂等**，`granted:false` 就是"今日已领"。
- 刷新：空 body → 400 `{"code":100000,"message":"request_body_error"}` → 接口存在，但 body 字段名没逆向出来（记进 E-037 未解）。
- 设备头：带不带 `X-Client-Device-ID` 对 `balance` 与 `model_catalog` 都 200 且结果一致 → 它不影响读，只影响"信任设备"判定。

#### 设计（写了 ADR-0010 + `docs/02-design/07-account-pool.md`）

十条核心决定：

1. **号池是并列的第二身份来源，不替换 `authSource` 三态。**
2. **`poolEnabled` 默认 `false`** —— 号池会自动花掉积分，必须显式打开。
3. **成员显式勾选、新号 `enabled:false`、空池绝不退化成"全部账号"**（workbuddy 原话："那是唯一会花掉你没授权过的积分的解读"）。
4. `accounts.json` 单文件多 token，`0600` + 原子写，**不拆不并入 `token.json`**（后者是"当前账号"）。
5. 选号在 `resolveApiKey`（每次请求一次）、记测量在 `onResponse`（拿得到 status）。
6. **HTTP 400 不换号、流中途断开不换号。**
7. 排序五条：①可用优先 ②`daily` 降序 ③`available` 降序 ④`expiresAt` 降序 ⑤`id` 升序。
8. 签到先查后写、单个失败不中断整批、**与开关无关**。
9. **"独立环境" = 每账号一个稳定随机 `X-Client-Device-ID`**（`raccoon-` + 32 hex），`x-client-platform` 恒 `desktop-windows`。**不是指纹伪造、不承诺防封。**
10. 加账号复用 `LoginFlow.start()`，加 `LoginMode = "primary" | "pool"` 维度；池模式**不写 `token.json`、不改主登录相位**。

#### 三个技术难点

**① 设备身份是"名册级"属性，不是请求级。** `profileOptions()` 不透传 `options.headers`，所以只能在 descriptor 的 `headers` 里注入（`createClient()` 把 `model.headers` 展开进 `defaultHeaders`，`openai-completions.js:539`）。推论：**换号必须重建名册**，指纹末尾加 `|dev:<deviceId>` 才能触发"先释放再注册"。

**② 会话粘住。** `sortForUse()` 的输入含余额读数，读数会在一轮对话中途刷新。不粘住会导致中途换号、会话 id 与设备身份一起变，上游看到"一个人在两台设备上接力说话"。所以 `resolvePoolAccount()` 先试 `poolActiveId`，只有它冷却了才重新排序。

**③ session id 必须按池成员算。** `sessionIdForPublish()` 改成 `pooled?.principal ?? this.token?.principal`。换号还用上一个号的会话 id 等于"同一个会话换了个人在说话"。

# 第六条日志（22:05–22:35）：`recordMeasure()` 每轮对话重写一遍明文 token

## 今天做了什么

### 1. 发现：`onResponse` 是"每轮对话都跑"的，不是"换号时才跑"

`recordMeasure(status)` 挂在 `Publisher.sync()` 传进去的 `PublishAccountResolver.onResponse` 上，
而那个钩子是 pi-ai 的 `Api` 层 `onResponse` —— **每个 HTTP 响应都会触发**。

它做的事是：

```
this.accounts = this.accounts.map(...)     // 整表重建
void writePool(this.accounts)              // 整表原子写，含明文 token
logger.info("pool/measure", ...)           // 每条一次
```

于是：**用户每说一句话，所有账号的明文 token 就往磁盘刷一遍，日志里多一条 `pool/measure ok`。**
号池开着的时候这不算 bug（写得对，只是多），但它是那种"上线之后才发现磁盘 IO 奇怪"的东西。

### 2. 改法：规则抽成纯函数，只拦"`ok` → `ok`"

`packages/dsh-raccoon-web/src/host/pool.ts` 新增：

```ts
export function shouldPersistMeasure(previous: PoolMeasure | undefined, next: PoolMeasure): boolean {
  if (next.state !== "ok") return true;
  return previous?.state !== "ok";
}
```

四条规则（PO-36 ~ PO-40 逐条断言）：

| 从 | 到 | 写盘 | 理由 |
| --- | --- | --- | --- |
| 无 | `ok` | ✅ | 首次确认可用 |
| `ok` | `ok` | ❌ | 唯一被拦的 |
| 冷却态 | `ok` | ✅ | 解除冷却的唯一记录 |
| 任何 | 非 `ok` | ✅ | 冷却必须立刻落盘 |

`recordMeasure()` 里换成 `if (!shouldPersistMeasure(pooled.measure, measure)) return;`。
**"不写盘"不等于"不做别的事"**：`measure.state !== "ok"` 时仍然 `poolActiveId = undefined` + `syncPublisher()`。

### 3. 顺手修掉一处注释漂移

`runAction()` 的文档注释还写着"八个 action 的分派"—— 那是 0.1.0 的数量，加号池后是 14 个。
改成准确版，并加一条硬约束：**新增 action 必须同时改三处**（`runAction()` 的 switch / `client.js` 里发起它的按钮 / `docs/02-design/07-account-pool.md` §5 的动作表）。
少改一处就会留下"界面上有按钮但宿主不认"或"宿主支持但没人调"的死代码。

# 第八条日志（23:05–23:20）：两个扫码入口共用一个 LoginFlow，池区把主登录的码当成自己的

## 今天做了什么

### 1. 一个真 bug：二维码串台

设置卡里有两个扫码按钮 —— 「登录」区的「扫码登录」（换当前账号）和「账号池」区的「扫码添加」（往池里加号）。
底下只有**一个** `LoginFlow`，而 `start(mode)` 的第一件事是 `cancel()`（把 `phase` 打回 `none`），然后才 `phase="pending"`。

于是：

1. 用户在池区点「扫码添加」→ `start("pool")`，池区显示二维码。
2. 用户又去上面点「扫码登录」→ `start("primary")`，取消上一轮并生成新码，`phase` **仍然是** `pending`。
3. 池区的判据原来只判 `phase === 'pending' || 'logging'` —— 依然为真，于是**池区继续显示一张已经属于主登录的二维码**。
   用户扫完，token 写进 `token.json`，池里什么也没多。他会以为是"扫码添加没生效"。

反向同理：池区在等码时，登录区会把池的码显示成"换当前账号"的码。

### 2. 修法：status 里带 `mode`，两个区各自认领

- `LoginSnapshot.mode: "primary" | "pool"`（`src/host/login-flow.ts`），`snapshot()` 一律带上；
- `loginBlock()`（`src/host/routes.ts`）透传成 `StatusLogin.mode`；
- `cancel()` / `markReady()` / `markDead()` / `complete()` 的池分支都把 `mode` 收回 `"primary"`
  —— 这四个时刻都意味着"这一轮扫码结束了"，留着 `pool` 会让前端以为还有一张池的码在等；
- 池区判据加 `login.mode === 'pool'`；登录区在 `mode === 'pool'` 时不显示二维码，改显示
  `loginPoolBusy`（"二维码在下面的「账号池」区域，扫完不会改变当前账号"）。

**为什么不用"哪个按钮最后被点"**：点击状态只活在前端内存里，刷新页面、换窗口、宿主重启就没了；
`mode` 是宿主侧的事实，`status` 每次轮询都带着它，前端重开也能对上。

### 3. 新增两条单测

- **ST-18b**：`loginBlock` 透传 `mode`；没有 `mode` 时**不凭空造**（`"mode" in bare === false`）。
- **ST-18c**：`LoginFlow` 的 `mode` 生命周期 —— 初始 `primary`；`start('pool')` → `pool`；
  `cancel()` / `markReady()` / `markDead()` 之后都必须回到 `primary`。
