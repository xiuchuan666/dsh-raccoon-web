## R1 网关改协议

**概率 高 / 影响 高**

小浣熊网关是私有 API，没有版本承诺、没有变更日志、没有弃用期。这是**唯一必然发生**的风险 —— 不是"会不会"，是"什么时候"。

### 触发信号

| 症状 | 可能原因 |
| --- | --- |
| `model_catalog` 返回结构变了 | `data.categories` 改名或层级变化 |
| 模型列表突然只剩 1 个 | 目录字段名换了，解析器读不到 |
| 对话 400/422 | 请求体字段改了（`max_tokens` → `max_completion_tokens` 之类） |
| 思考内容消失 | `delta.reasoning_content` 改名 |
| 二维码登录成功但 catalog 401 | `iam/confirm` 的 cookie 机制变了 |
| 突然全部 404 | 路径前缀 `/api/web/llm/v2` 升级到 v3 |

### 影响

插件完全不可用，且**症状可能是静默的**（比如模型列表空了但界面不报错）。

### 应对

1. **三层分层**（[ADR-0004](../02-design/adr/0004-protocol-adapter-split.md)）—— 改动集中在 `src/protocol/`，不动 UI 和宿主
2. **`05-empirical-findings.md`** —— 每次网关行为都带时间戳记下来，改协议时能对比"以前是什么样"
3. **诊断块** —— 用户报障时能一眼看出是哪个端点变了
4. **抓包脚本** `scripts/probe-gateway.mjs` —— 一键把四个端点都打一遍，输出人类可读的对比

### 缓解设计（已内建）

- **目录解析多键名兼容**：`context_window` ?? `contextWindow` ?? `max_context_length`（[catalog.ts](../02-design/01-module-map.md)）
- **积分解析多字段兼容**：`available_points` ?? `total_chargeable_points` ?? `total` ?? `balance` ?? `points`
- **帧解析宽松**：不认识的帧 `return null` 而不是抛错（CH-9）
- **catalog 探测是权威**：`iam/confirm` 失败不致命，以 catalog 能不能读为准

### 为什么会发生

上游在持续迭代产品，每次前端发版都可能改接口。他们已经改过一次（`/llm/v1` → `/llm/v2`）。

## R2 自实现二维码扫不出来

**概率 中 / 影响 高**

二维码编码器（[ADR-0002](../02-design/adr/0002-self-contained-qr-encoder.md)）370 行，其中至少五处一旦写错就"看起来正常但扫不出来"：

| 易错点 | 症状 |
| --- | --- |
| 版本 ≥7 没写版本信息块（两处 18bit） | 手机识别出"版本"但读不出数据 |
| 对齐图案位置错 | 低版本正常、高版本扫不出 |
| 版本 ≥5 分块交错错 | 扫出来是乱码 |
| 掩码与格式信息不一致 | 完全扫不出 |
| 格式信息只写一处 | 某些角度扫不出 |

**本项目的内容是 149 字节 → 版本 8**（E-007），意味着**必然触发"版本 ≥7 要写版本信息块"和"版本 ≥5 要分块交错"两条**。这不是边缘情况，是必经路径。

### 触发信号

- 手机扫不出
- 手机扫出来但内容是乱码
- 手机上打开的页面缺 `appname` 参数

### 应对

| 阶段 | 措施 |
| --- | --- |
| 开发时 | 写完先用 `qrencode` / 在线解码器验证一次（**允许一次性引入外部工具，不进依赖**） |
| M1 完成标准 | 必须用真手机扫一次，结果记进 `05-empirical-findings.md` |
| 回归 | QR-7（版本信息块存在）、QR-8（时序图案）、QR-10（格式信息两处）三条单测守住 |
| 兜底 | 触发条件：**累计 3 小时调不出来** → 立刻切 `qrcode-generator`（40KB，零传递依赖），把 QR 模块换成薄封装 |

### 为什么兜底阈值是 3 小时

因为引库的代价（+40KB、+1 依赖）**远小于**卡在这一步的代价。ADR-0002 里选择自实现是为了零依赖，但零依赖是**手段**不是目的 —— 目的是"插件能装上不冲突"。40KB 的无传递依赖库不会造成冲突。

## R3 自定义 pi-ai Api 写不出来

**概率 中 / 影响 中**

[ADR-0003](../02-design/adr/0003-reasoning-channel.md) 决定自己写一个 pi-ai `Api` 来塞 `extra_body` 和解析 `reasoning_content`。风险在于：pi-ai **没有任何 .d.ts**（E-010），`Api` 接口的形状只能从编译产物反推。

### 触发信号

- 反推不出 `Api.stream()` 的正确签名
- 事件流协议对不上（DSH 侧不渲染 / 渲染错乱）
- 工具调用 index 累积出错

### 应对

| 阶段 | 措施 |
| --- | --- |
| 反推 | 三条命令（见 ADR-0003）：读 `openai-completions.js` 的 `export`、找 `drainEvents` 的用法、对比 `anthropic-messages.js` |
| 参考 | `dsh-llm-adapters/lib/index.js` 里的 `openAiStream()` 是**已验证可用**的同构实现（8973 行文件里搜 `async function* openAiStream`） |
| **兜底** | 8 小时不通 → 切 `openAICompletionsApi()`，`reasoning: false`，UI 说明"该模型不支持思考展示" |
| 兜底的兜底 | 如果连 `openAICompletionsApi()` 都不通（比如 baseUrl 拼接问题），退回继承 `LlmAdapter`（[ADR-0005](../02-design/adr/0005-pi-ai-adapter-over-raw-llmadapter.md) 否决的路线 A） |

### 影响为什么是"中"不是"高"

因为有三层兜底，最差情况是"没有思考内容展示"，插件仍然能用。**思考通道是加分项，不是前置条件**。

## R4 反爬 / 风控把插件流量识别出来

**概率 中 / 影响 高**

小浣熊有网页端和桌面端。插件从 Node 进程发请求，**天然缺少**浏览器指纹：没有 `sec-ch-ua`、没有 `origin`、没有 `referer`、没有 cookie 罐、TLS 指纹也不是 Chrome 的。

### 触发信号

| 症状 | 含义 |
| --- | --- |
| 一开始能用，几小时后开始 401 | 被判定为异常会话 |
| catalog 正常但 chat 403 | 对话接口有额外校验 |
| 需要过验证码 | 已经触发了风控 |
| 桌面端能用、插件不能用 | 有 `x-client-platform` 之外的校验 |

### 应对（已内建）

| 措施 | 说明 |
| --- | --- |
| 复刻客户端头 | `x-client-platform: desktop-windows` + `x-client-version: v1.0.35` + `x-raccoon-language: zh` + `x-org-code: ""` |
| **稳定 session id** | `sess-0-<sha256(principal+model)[:8]>` —— 每次请求新 id 会让网关看到"一个账号几分钟开了几百个会话"（这是 dsh-llm-adapters 从官方客户端抓包反推出来的） |
| 复用 token 而非反复登录 | 登录只发生在用户主动扫码时 |
| 不并发轰炸 | 重试上限 2 次、退避 1.5s→10s |

### 不做的（明确不做）

| 不做 | 理由 |
| --- | --- |
| 伪造 TLS 指纹 | 需要改 Node 的 TLS 栈，会把插件变成"专业反检测工具"，性质变了 |
| 伪造 `sec-ch-ua` 等浏览器头 | Node 里发这些头本身就是异常信号，反而更容易被识别 |
| 代理池 | 一个用户一个账号，不需要换 IP |
| 打码平台 | 目前不需要过验证码 |

**这几条不是"技术上做不到"，是"做不到也不该做"** —— 一旦开始伪造浏览器指纹，这个项目的性质就从"个人账号的客户端替代品"变成"绕过风控的工具"，风险等级完全不同。

### 最坏情况

账号被临时限制 → 用户等几小时或联系客服。**插件必须给出可理解的提示**，而不是静默失败。

## R5 DSH 内核升级破坏契约

**概率 中 / 影响 中**

插件依赖的内核 API：
- `ctx.llm.registerAdapter`
- `ctx.settings.register` / `configure`
- `ctx.webServer.register`
- `PiAiAdapter` 的构造函数形状
- `createProvider` / `Api` 接口

这些都是**内部 API**，没有稳定性承诺（内核包连 `.d.ts` 都没有 —— E-009）。

### 触发信号

- DSH 升级后插件加载失败
- `INVALID_ADAPTER` / `DUPLICATE_ADAPTER` 报错
- 模型列表空了但日志无错
- `client.js` 的两个 slot 不渲染

### 应对

| 措施 | 说明 |
| --- | --- |
| peerDependencies 逐段并集 | 明确支持哪些版本，新版 DSH 不匹配时**安装就报错**而不是运行时炸 |
| 改动集中 | 内核交互只在 `src/index.ts` + `src/host/publish.ts` + `src/provider/adapter.ts` 三个文件 |
| 类型桩 | `src/types/dsh.d.ts` 就是我们依赖的**完整清单** —— 升级时对着它逐条核 |
| 保守的 `engines` | 跟宿主一致（`^22.19.0 \|\| >=24`），不激进 |

### 参考

`dsh-connect-workbuddy` 的 README 里维护了一张"支持的 DSH 版本"表，每次内核变化都在里面记。我们照做。

## R6 账号被限流到不可用

**概率 中 / 影响 中**

小浣熊按**账号 token 速率**限流（不是每分钟请求数）。一轮对话上下文越大越快撞到，且**上游不给恢复时间**。

### 触发信号

- 长对话进行到一半开始 429
- 换模型也不行（按账号限，不是按模型限）
- 等一会儿能恢复一点，但很快又撞到

### 应对

| 措施 | 说明 |
| --- | --- |
| `contextCap` 默认 128000 | 不把网关的 1M 上下文全用上。**这是主动降级换可用性** |
| 明确的文案 | 那条长文案（[05-error-model](../02-design/05-error-model.md)）解释"是按 token 速率不是请求数"，用户才知道该缩上下文而不是重试 |
| ~~RATE_LIMIT 不重试~~ | 重试只会延长冷却 —— 这是相对 sensenova（`maxRetries: 8`）的关键差异 |
| 不做自动重连 | 浣熊没有 `Last-Event-ID` 续传，重连等于又发一次完整上下文 |

### 为什么 `contextCap` 是 128000

- 太小（32k）：长文档分析做不了
- 太大（1M）：一进去就撞限流，用户会觉得"这插件不能用"
- 128k：**能做完大部分任务，且留出足够的吞吐余量**

这个值是**可调的**（settings 里），用户嫌小可以自己往上调 —— 但默认值要保守。

## R7 `client.js` 加载失败且无日志

**概率 中 / 影响 中**

`client.js` 是 classic script，通过 `globalThis.__ModuleLoader__.load({...})` 注册。它有两个特性：

1. **任何语法错误 → 整个文件不执行，且只在浏览器 console 里报错**（DSH 的宿主日志里没有）
2. **不能有 `import` / `export`** —— 有就是语法错误

### 触发信号

- 设置卡里没有「小浣熊」
- 输入框左侧没有 🦝
- 宿主日志里 `[raccoon-web] loaded` 有，但 UI 上没有

### 应对

| 措施 | 说明 |
| --- | --- |
| `__ModuleLoader__` 早退 | `if (loader === undefined) { console.warn(...); return; }` |
| `const BUILD = "..."` + `globalThis.__DSH_BUILD_raccoon = BUILD` | 在浏览器 console 里 `__DSH_BUILD_raccoon` 就能确认加载的是哪一版 |
| `verify-install.mjs` 第 4/5 条 | 检查 `client.js` 不以 `import`/`export` 开头、含 `__ModuleLoader__` |
| 结构极简 | 不用 JSX、不用 class 语法糖以外的东西、不用可选链之外的新语法（保守） |
| 顶层 try/catch | 整个 `apply` 包一层，出错就 `console.error("[raccoon-web] client apply failed", e)` |

### 排障路径（写进 troubleshooting）

```
F12 → Console
1. 有没有 __ModuleLoader__？       没有 → 不是我们的问题，宿主没起
2. 有没有 __DSH_BUILD_raccoon？    没有 → client.js 没执行（语法错误）
3. 有没有 [raccoon-web] 的 error？ 有 → 看堆栈
4. Network 里 /plugins/dsh-raccoon-web/status 200？  403 → 不是 loopback
```

## R8 核心开发者失去兴趣

**概率 中 / 影响 高**

这是个人项目。最大的失败模式不是技术问题，是**三周后回来发现看不懂自己写的东西**。

### 触发信号

- 打开仓库不知道从哪开始
- 忘了为什么这么设计
- 改一个地方要读五个文件

### 应对（已内建）

| 措施 | 说明 |
| --- | --- |
| **文档优先** | `AGENTS.md` 规定先读顺序，`devlog/` 是唯一可靠的"上次做到哪" |
| **ADR 记录"否决了什么"** | 六篇 ADR 每篇都有"否决的替代方案 + 理由"，回来时不用重新推演 |
| **单文件 ≤800 行** | 反例：sensenova 9442 行、workbuddy 619KB —— 那种规模只有原作者能维护 |
| **三层分层** | 改网关协议时不用碰 UI |
| **每个决定带实测证据** | "为什么用版本 8" 有 E-007，不用重新算 |

### 为什么概率是"中"

因为**已经有六份前人实现死在这里**：`dsh-raccoon-connect` 停更、`dsh-raccoon` 0.0.1 是空壳、`magpie-raccoon-auth` 是移植的孤儿。这不是猜测，是观察到的模式。

## R9 上游直接封禁此类插件

**概率 低 / 影响 高**

上游可能：
- 在服务条款里明确禁止第三方客户端
- 加设备指纹校验（绑定 `clientDeviceId`）
- 加签名校验（请求体签名）

### 触发信号

- 所有第三方实现同时失效（社区反馈）
- 需要 `clientDeviceId` 之外的新头
- 请求体出现未知签名字段

### 应对

| 措施 | 说明 |
| --- | --- |
| **不公开分发** | 见 [03-release-plan §7](03-release-plan.md#7-为什么不发-npm-公网) —— 不引起注意是最好的应对 |
| **协议库可独立** | `src/protocol/` 不依赖 DSH，可以拿去做别的客户端 |
| **不伪造指纹** | 见 R4 —— 一旦开始伪造，就从"自用"变成"对抗" |
| **接受它可能死** | README 里明说"不保证长期可用" |

### 为什么概率是"低"

上游目前对第三方客户端**没有明确态度**（既没支持也没封）。而且桌面端本身就是个 Electron 客户端，请求形态跟我们的实现很接近。

## R10 Windows 路径与权限差异

**概率 低 / 影响 低**

本机是 Windows（`win32 x64`），但代码要考虑跨平台。

### 触发信号

- 路径分隔符错（`\` vs `/`）
- `0o600` 权限位无效（Windows 上 chmod 对普通文件基本无效）
- 长路径（>260 字符）

### 应对

| 措施 | 说明 |
| --- | --- |
| 全部用 `node:path` 的 `join` / `resolve` | 不手拼字符串 |
| 不依赖权限位 | Windows 上 `0o600` 写不进去也不报错，所以**不能靠它做安全边界** —— 真正的边界是"token 永远不进浏览器" |
| 路径短 | `~/.dsh/profiles/desktop/raccoon-web/` 不到 60 字符 |

| 里程碑 | 主要暴露的风险 |
