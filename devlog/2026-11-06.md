# 2026-11-06 · 第三条日志：换路线（桌面端凭据）并跑通真链路

## 今天做了什么（第三段）

### 1. 用户提出换路线

原话（m01681）：**"不可用像 workbuddy 那种反代的方式吗，不需要登录直接接入本地客户端的登录状态"**。

之前连着 4 张码都"刚生成就过期"，用户已经不打算再扫了。这个要求很合理，而且方向是对的 —— 只是当时我以为"workbuddy 那种方式"是"读 workbuddy 的本地文件"。

### 2. 先排掉 workbuddy 本身

读了 `dsh-connect-workbuddy@5.17.0` 的 `lib/index.js`：

- `homedir()` 只用于探测 npm/nvm/fnm/volta/pnpm/yarn 的全局 bin；
- `.workbuddy-pool` 存的是**探测结果**（`outcome` / `atMs` / `retryAtMs` / `message`），源码注释明写"存的是观测结果而非凭据"；
- 它自己的凭据在 `$DSH_HOME/.workbuddy-auth.<region>.json`，是 OAuth（`/auth/state?platform=` → 浏览器授权 → `/auth/token?state=`）换来的。

**结论：workbuddy 并没有"读本地客户端登录态"这个能力**，它只是把 OAuth 做得无感。所以"照抄 workbuddy"字面上做不到，能做的是抄它的**产品形态**。

### 3. 找回真正的凭据入口（E-006 是错的）

E-006 当时只 `ls ~/.box-agent/config/auth.json`，不存在 → 判定"本机没有桌面端登录态"。**这个判定坑了我一整天。**

### 5. 顺手修了三处目录解析错误（E-032）

拿真目录一比对，发现我们写错三处：

| 我们以为 | 实际 |
| --- | --- |
| `context_window` / `max_tokens` 在顶层 | 在 **`params`** 嵌套对象里 |
| 显示名是 `name` / `display_name` | 是 **`description`**（`"Kimi-K3"`），`name` 与 `model_name` 都是 id |
| 倍率是 `multiplier` / `points_multiplier` | 是 **`billing_multiplier`** / `billing_effective_multiplier` |

还有一处：分类对象只有 `{type:"chat", default_model}`，**没有 `key`/`name`** → 分组 key 必须取 `type`，否则恒为 `"default"`。

### 6. 逆向出第二套扫码协议（E-033）

asar 里 `createAccountQrSession`：

```js
const code = `${Date.now()}${randomBytes(16).toString('hex')}`;   // 本地生成，45 字符
url.searchParams.set('appname', '小浣熊官网');                      // 不是「商汤小浣熊」
```

轮询端点也不同：`POST /api/web/auth/v1/login_with_qrcode_code`，不是 `/api/iam/v1/auth/mp/qrcode/login`。

实测交叉验证：Web 码打 IAM 端点回 `AUTH_QRCODE_INVALID` → **两套命名空间不通用**；`login_with_qrcode_code` 对任何格式正确的 code 都回 `pending`（含乱编的）→ **这个端点没有"code 有效性"概念**。

于是新增 `qrProtocol: "web" | "iam"`，默认 `web`（[ADR-0009](../docs/02-design/adr/0009-web-auth-qr-protocol.md)）。真宿主里生成的 Web 码被 OpenCV **双检测器一致解出**，`appname` 正确、code 45 位。

### 7. 两个真实 bug（都是"照抄形状但抄错了契约"）

**bug 1：`auth.apiKey.resolve()` 恒返回 `undefined`。**

`packages/dsh-raccoon-web/src/provider/adapter.ts` 里我照抄了 sensenova 的形状，但漏了返回值。结果 pi-ai 抛 `Provider is not configured: raccoon-web`，被 `toStreamChunks` 归成 `PI_AI_ERROR`，界面只说"出错了"。

修好后真链路：`block-start → reasoning-delta ×27 → text-delta → usage → finish`，首字节 **1637ms**，思考 324 字，正文 `"2"`。

**bug 2：`registerAdapter` 的 `replace()` 返回 `void`，且换不掉 adapter 实例。**

我以前写的是 `this.handle = this.handle.replace({providers, adapter})`。真实契约（`dsh-llm/lib/index.js:1856`）：

```ts
export interface AdapterRegistrationHandle {
    (): void;
    replace(providers: string[]): void;   // ← 参数是 string[]，返回 void
}
```

于是第一次 replace 后句柄变 `undefined`，第二次 sync 抛 `providers is not iterable`。

更关键的发现：**`adapter` 是构造时闭包捕获的，`replace` 换不掉实例**。而本插件换名册必须换 `PiAiAdapter` 实例（`current()` 用 `profiles()` 引用相等做 memo）。**结论：`replace` 对本插件完全无用**，改成 `release()` + `registerAdapter()`，与 sensenova 的 `swapRegistration` 一致。

单测没抓到这条，因为假 handle 的 `replace` 被我写成"返回 handle 自己"——**照抄了错误假设**。修测试比修代码更重要。

### 根因（逆向内核 slot 契约后确定）

设置对话框左侧菜单走的是 **`settings.section`** slot（kind=list, scope=root），而 `client.js` 只注册了：

- `conversation.input.left`（输入框左侧积分药丸）
- `plugins.bundle.config`（**「插件」面板 → 已安装列表 → 点开包详情页**才渲染，不是设置对话框）

两者都不是设置对话框，所以设置卡压根没出现在用户看的界面，`contextCap` 输入框无从谈起。决定性证据：

- `dsh-cordis-client-runner/lib/client.js:5340-5395` 定义 `settings.section`，`id` required、`order` 升序、`label` 可为 thunk，官方 example 用 `ctx.slots.inject("settings.section", () => ctx.slots.register({name,id,order,label}, Component))`；
- 内置真实 order：`account -10` / `models 10` / `plugins 15`；
- 第三方同款（用户截图里「侧边卡片」的来源）：`profile/node_modules/dsh-better-sidebar/lib/client.js:33050-33059` 用 `order:100, label: () => t("settingsNav"), inject: () => ({store, service})` 注册出顶层菜单项；

- `slots.inject()` 是能力探测：slot 声明存在时回调才跑，注册项必须带 `id`（用 `key` 会静默不显示）。

### 改动（代码）
