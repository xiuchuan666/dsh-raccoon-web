# ADR-0002 · 自己实现二维码编码器，不引 `qrcode`

- 状态: Accepted
- 日期: 2026-11-06
- 决策者: 项目所有者
- 相关: [E-007](../01-research/05-empirical-findings.md)、[E-011](../01-research/05-empirical-findings.md)

---

## 背景

登录页要显示二维码。二维码内容是一条 149 字节的 URL（E-007）。

可选方案：

| 方案 | 代价 |
| --- | --- |
| A. `import "qrcode"` | 新增 ~180 KB 运行时依赖 |
| B. `import "qrcode-generator"` | 新增 ~40 KB 依赖 |
| C. 自己实现 | 约 350 行，需要正确处理 RS 纠错 + 掩码 + 版本信息 |
| D. 调第三方 QR 生成 API（如 `api.qrserver.com`） | 把登录 URL（含 `code`）发给第三方 |

---

## 决策

**选 C：自己实现。**

- 只支持 **byte 模式 + 纠错等级 M + 版本 1–10**
- 输出 SVG 字符串（不生成 PNG，不依赖 canvas）
- 不新增任何 npm 依赖

---

## 理由

### 1. 插件跑在宿主进程，依赖冲突会拖垮整个 app

这不是普通的 node 项目。这个包被 `import()` 进 Electron 主进程，和 DSH 的全部依赖共享一个解析树。

一个 `qrcode` 依赖如果带入不兼容版本的 `dijkstrajs` / `pngjs` / `yargs`，可能：
- 让 DSH 自己的某个依赖解析到错版本
- 增加几百 KB 的启动加载时间
- 在 `pnpm` 的严格 node_modules 布局下干脆解析失败

**收益（省 350 行代码）远小于风险。**

### 2. 功能需求极窄

我们只需要：

| 需求 | 值 |
| --- | --- |
| 内容 | 一条 149 字节的 ASCII URL |
| 纠错 | M（15%，手机扫码的常用档） |
| 版本 | 8（149 字节 → 152 容量） |
| 输出 | SVG |
| 纠错算法 | Reed-Solomon over GF(256) |
| 掩码 | 8 种，按 penalty 选最优 |

不需要：多编码模式（数字/字母/汉字）、多纠错等级、PNG、Logo 嵌入、颜色渐变、容错容错再容错。

**用 5% 的功能去引一个通用库，是典型的过度依赖。**

### 3. 第三方 API 会把登录 code 泄露出去

方案 D 直接否决。二维码内容里有 `qrcode_code`，那是**正在进行的登录会话的凭据**。发给任何第三方都等于把登录流程交出去。

### 4. 可测

自己实现的编码器能被单元测试覆盖：

```ts
test("qr: 149 字节选版本 8", () => assert.equal(pickVersion(149), 8));
test("qr: 版本 8 必须写版本信息块", () => {
  const m = buildMatrix(SAMPLE_URL);
  // 版本信息块在 (0, 8..10) 和 (8..10, 0) 的镜像位置
  assert.ok(hasVersionInfo(m));
});
test("qr: 定位图案角点正确", () => {
  const m = buildMatrix(SAMPLE_URL);
  assert.equal(m[0][0], 1); assert.equal(m[0][6], 1); assert.equal(m[6][0], 1);
  assert.equal(m[7][7], 0);   // 分隔符
});
```

引一个库就只能测"我调对了 API 没有"，测不到"生成的码能不能扫"。

## 实现要点（容易写错的地方）

### 1. 版本 ≥ 7 必须写版本信息块

18 bit，BCH(18,6)，放在两个位置：

```
右上： (row 0..5, col size-11..size-9)
左下： (row size-11..size-9, col 0..5)
```

**参考实现只写到版本 10，但很多简化实现漏了这段** —— 结果是自己扫得出来（读码器容错），手机扫不出来。这一条必须有测试。

### 2. 版本 ≥ 2 有对齐图案

位置表（版本 1–10）：

| 版本 | 对齐图案中心坐标 |
| --- | --- |
| 1 | 无 |
| 2 | 6, 18 |
| 3 | 6, 22 |
| 4 | 6, 26 |
| 5 | 6, 30 |
| 6 | 6, 34 |
| 7 | 6, 22, 38 |
| 8 | 6, 24, 42 |
| 9 | 6, 26, 46 |
| 10 | 6, 28, 50 |

笛卡尔积，**跳过与定位图案重叠的三个角**。

### 3. 数据分块与交错（版本 ≥ 5）

版本 8-M 的块结构：**4 个块，每块 58 数据码字 + 22 纠错码字**（具体值查表）。

交错规则：先按列取所有块的第 0 个数据码字，再取第 1 个，……；纠错码字同样交错。

**写错这个，二维码看起来正常但扫不出来。**

### 4. 掩码选择

8 种掩码，每种算 penalty（N1=3 连续同色、N2=3 2×2 同色块、N3=40 类似定位图案、N4=10 黑白比例），选 penalty 最小的。

**格式信息要跟着掩码走**（`(ecBits << 3) | mask`，BCH(15,5)，`^ 0b101010000010010`）。

### 5. 格式信息写两遍

左上角一份，右上+左下拼接一份。只写一处 → 扫不出来。

## 后果

### 正面

- 零依赖
- 350 行可测代码
- 容量上限明确（213 字节），超了抛可读错误

### 负面

| 代价 | 缓解 |
| --- | --- |
| 350 行要自己维护 | 算法是 1994 年定的标准，不会变。写完就不用动 |
| 只支持 M 级 + byte 模式 | 我们的场景只需要这个 |
| 只到版本 10（213 字节） | 149 字节够了；超出时抛"二维码内容超出编码器容量，请反馈" |

### 风险

**最大的风险是"生成出来了但扫不出来"。** 缓解：

1. 版本 8 的完整 fixture 测试（对照已知正确的矩阵）
2. 实现完成后用真实手机扫一次（联调阶段的第一件事）
3. 用 `zbarimg` 或手机原相机交叉验证

如果实现失败，兜底是**引 `qrcode-generator`（40 KB，无传递依赖）**。这个兜底写在 [04-risks](../03-plan/04-risks.md) R2。

---

## 复审条件

1. 需要版本 > 10（内容超 213 字节）
2. 需要非 byte 模式（比如纯数字的短内容，能塞进更小版本）
3. 实现完成后手机扫不出来，且两天内修不好 → 立刻切 `qrcode-generator`
